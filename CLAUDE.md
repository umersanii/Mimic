# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This repo is the open-source project **Mimic** (`umersanii/Mimic` on GitHub). Reference/technical
documentation lives in a separate sibling repo, **Mimic-docs** (`umersanii/Mimic-docs`, MkDocs +
Material, at `/home/sani/c0d3/Mimic-docs` locally) — update it alongside code changes when behavior
documented there changes, not just this repo's own README.

## Learning goal for this project

The user's primary aim with this repo is to **maximize their own robotics learning**, not to have Claude Code drive raw output. They want to engage as the **architect/systems designer** of this project — understanding tradeoffs, making the calls, and building intuition for how the pieces (vision, control, firmware, simulation) fit together — rather than reading or reviewing implementation line by line.

Sessions in this repo should be steered accordingly:
- Explain the *why* behind architectural and design choices (e.g. why a given simulation approach, joint model, or control scheme), not just deliver working code.
- Default to surfacing decisions and tradeoffs to the user rather than silently picking one — this project is a vehicle for the user to practice making those calls.
- Favor conceptual/systems-level explanation over walking through code line by line, unless the user explicitly asks for a code-level review.
- It's fine to still write and run code — the point is to keep the user in the architect's seat and build their robotics understanding along the way, not to withhold implementation.

### Simulation — now Gazebo, not Isaac Sim

The hand project's simulation work has moved to **Gazebo Sim (Harmonic) + ROS2 Jazzy**, in `sim/` — a separate track from the `isaac-sim-setup.md` runbook above (that doc is retained for reference/other uses, but the hand isn't simulated in Isaac Sim).

- `sim/docker/` — Dockerfile builds `robotics-gazebo` image (Ubuntu 24.04 + gz-harmonic + ROS2 Jazzy ros-base + ros_gz). `sim/docker/run.sh` mounts the whole `sim/` dir to `/sim` in the container (not just `worlds/`) and sets `GZ_SIM_RESOURCE_PATH=/sim/models`, since mesh files live under `sim/models/`.
- `sim/worlds/box_world.sdf` — primitive-shape joint/physics learning rig (pendulum, hinge, box), uses `dartsim`.
- `sim/worlds/hand_world.sdf` + `sim/models/hand/{left,right}/` — the InMoov-derived dual-hand model (see below). **Uses `bullet-featherstone`, not `dartsim`** — see the mimic-joint constraint below for why.
- `sim/worlds/hand_world.sdf` also stages a `workbench` (table) and `backdrop_wall` around the hands, plus two dim point fill lights alongside the sun. **Gotcha: bullet-featherstone rejects any model with more than one link and no joints connecting them** — errors "Multiple sub-trees / floating links detected... not supported in bullet-featherstone implementation yet" at load, even for `<static>true</static>` props with no physics need for a joint tree. The `workbench` model (table top + 4 legs) is therefore one link with 5 collision/visual elements, not 5 links — any future static multi-part prop in this world must follow the same pattern.
- Backdrop placement is tied to the existing overview camera's viewing direction: the `<gui><camera>` pose `0.5 0.5 1.3 0 0.3 -2.35` sits at +x/+y looking toward the origin, so the open/front side is +y and "behind" the hands is -y — `backdrop_wall` is placed at `y=-0.45` for that reason. Moving the overview camera pose without checking this will point it back through the wall. `fill_light_left`/`fill_light_right` follow the same convention (`y=+0.6`, camera side) — they were originally placed at `y=-0.6` (past the wall, on the "behind" side) by mistake and did nothing since the wall blocked them from the hands.
- Shadows are back on for the `sun` light (previously fully disabled — see the shadow-acne note below). To do that without reintroducing the acne, `cast_shadows` is set `false` on each of the 36 individual finger-segment `<visual>` elements (the actual acne source: many small, close-packed meshes) while left at its default `true` for `hand_link`/`forearm_link` and the workbench/backdrop — this still gets a visible overall hand/arm shadow without the small phalanx meshes flickering. Any new small finger-adjacent visual added to the hand model should get the same `cast_shadows=false` treatment.
- `sim/worlds/gui/{left_hand,right_hand}.config` are `--gui-config` launch profiles for camera presets (`gz sim -g sim/worlds/gui/left_hand.config /sim/worlds/hand_world.sdf`, from inside the container) — stock gz-sim has no in-session clickable preset switcher, so "presets" here means picking a config file at launch, not a live toggle. The default launch (no `-g` flag) uses the world's own overview camera.
- **Combined web dashboard (built)**: `vision/dashboard/` (FastAPI + WebSocket, started via `hand_tracker.py --dashboard`, serves `http://localhost:8765/`) now shows both the webcam feed *and* a live sim camera feed side by side, one browser tab. The two video panels are two independent WebSocket connections to two independent servers — they are not routed through each other:
  - **Vision panel**: `vision/dashboard/server.py`'s `DashboardHub`, fed per-frame from `hand_tracker.py`'s own capture loop (unchanged from the vision-only dashboard — see `vision/hand_tracker.py`'s `--dashboard` flag).
  - **Sim panel**: `sim/bridge/gz_camera_dashboard.py`, runs *inside* the `robotics-gazebo` container (needs `gz.transport13`/`gz.msgs10`, same constraint as `gz_hand_bridge.py`), subscribes to a new `overview_camera` sensor's image topic in `hand_world.sdf`, and serves its own FastAPI/WebSocket server on port `8766` directly on the container's host network (`--network=host`). Launch once per container session via `sim/bridge/start_camera_dashboard.sh` (`docker exec -d`, detached — it has no stdin to pipe, unlike `gz_hand_bridge.py`). This is deliberately decoupled from `hand_tracker.py`'s process/lifecycle: the sim panel reconnects independently in the browser (`vision/dashboard/static/app.js`'s `connectSim()`) and just goes to a dimmed "NO SIGNAL" state if the bridge isn't running, without blocking the webcam panel.
  - **Why a real sensor was needed**: the existing `<gui><camera>` element (pose `0.5 0.5 1.3 0 0.3 -2.35`, see below) is a client-side-only viewport with no `gz-transport` topic — nothing outside the interactive GUI process can read it. `overview_camera` (in `hand_world.sdf`, placed right after `backdrop_wall`) is a real `<sensor type="camera">`; it's one more single-link static model (same bullet-featherstone "no multi-link joint tree" pattern as `workbench`/`backdrop_wall` above), publishing `gz.msgs10.image_pb2.Image` (`R8G8B8`, 640x480, 30Hz) on topic `overview_camera/image`. `gz_camera_dashboard.py` converts each frame to JPEG with Pillow (added to the Dockerfile via `pip install --break-system-packages` — Ubuntu 24.04's system pip otherwise refuses plain installs under PEP 668).
  - **Sensor pose does NOT reuse the GUI camera's pose** — that pose (`0.5 0.5 1.3 0 0.3 -2.35`, off-center in x and close to the backdrop wall's top edge at `z=1.5`) was tuned for a human to freely orbit from, not as a fixed unattended framing; used as-is it put most of the frame on bare wall, clipped both hands at the edges, and caught the bright void above the wall's `z=1.5` top. `overview_camera` instead sits at `0 0.85 0.78 0 0.12 -1.5708` — centered in x between the two hand mounts (`x=-0.2`/`x=+0.2`), on the open `+y` side facing `-y` toward the hands/wall, low enough to stay well under the wall's top edge. Tuned empirically: rendered single frames from an isolated throwaway container (`GZ_PARTITION` set to a unique value — `--network=host` containers here share the host's hostname, so gz-transport's default hostname-based partition would otherwise collide with a concurrently-running main session) and iterated pose values by inspection, not derived in one shot from geometry alone.
  - **Scope**: one overview camera only — not yet one per the `left_hand.config`/`right_hand.config` presets. That per-hand camera split is a natural follow-up, not built.
- **`dartsim` (the physics engine `box_world.sdf` uses) silently ignores `<mimic>` joints** in this Gazebo build — logs "physics engine does not support mimic constraints" and just leaves the joint unconstrained. Verified `bullet-featherstone` applies mimic correctly, **but only when the driver joint is proximal (attached directly to `hand_link`) and every mimic joint is downstream of it in the kinematic tree.** A driver joint with an *upstream* mimic joint (a mimic closer to the tree root than its own driver) silently gets zero effective torque — confirmed by testing (see below). Any new world file that relies on mimic joints must set `type="bullet-featherstone"` and add `<engine><filename>gz-physics-bullet-featherstone-plugin</filename></engine>` inside the `Physics` system plugin — don't copy `box_world.sdf`'s dartsim config for hand/mimic-joint work without changing this.
- **Hand model provenance (2nd generation)**: `sim/models/hand/{left,right}/hand.urdf` are generated by `sim/models/hand/generate_hand.py` (checked into the repo) from mesh + joint-origin data transcribed out of [MyRobotLab/inmoov_ros](https://github.com/MyRobotLab/inmoov_ros)'s `inmoov_description`/`inmoov_meshes` packages (CC-licensed — see `LICENSE.txt` copied into each side's directory). This replaced a 1st-generation model extracted from [Sentience-Robotics/inmoov_ros_sim](https://github.com/Sentience-Robotics/inmoov_ros_sim)'s whole-body sim rig, which had rougher meshes (that repo optimized for physics/joint structure, not visual quality) and only covered the left hand.
  - **Full regeneration pipeline** (needs `gz` on PATH, e.g. run inside the `robotics-gazebo` container): `python3 generate_hand.py` (writes `{left,right}/hand.urdf`) → `gz sdf -p left/hand.urdf > left/hand.sdf` (and the same for `right/`) → `python3 build_world.py` (assembles `sim/worlds/hand_world.sdf` from both sides' converted SDF — fixes up mesh URIs and visual material, since `gz sdf -p` needs relative-to-itself paths and silently drops URDF material colors; see `build_world.py`'s docstring).
  - **Why transcribed by hand instead of run through the real `xacro` toolchain**: the source repo's `asmHand.urdf.xacro` macro is parameterized by `side`/`flip` args exactly the way this project needs (mirrors correctly, no manual mirroring math), but its joint-limit properties resolve via `$(find inmoov_bringup)/config/config.yaml`, which needs real ROS package-path resolution — not worth standing up a colcon workspace for a one-time generation step. `generate_hand.py` hand-resolves the same macro logic (side/flip substitution) directly in Python instead.
  - **Joint limits/velocity do NOT reuse the source repo's `config.yaml` `minGoal`/`maxGoal`** (real per-servo calibration in degrees, tied to their specific hardware, not meaningful here) — kept at this project's existing `0..1.5708` rad / `0.7854` rad/s convention from the 1st-generation model, since `sim/bridge/gz_hand_bridge.py`'s `JOINT_MAX_RAD` scaling already assumes that range.
  - **Inertial values also do NOT reuse the source repo's `config.inertial.urdf.xacro` macros** — their mass units are ambiguous (raw value divided by 1000 lands in a "grams-look-like-kg" range with no unit documentation) and not worth trusting unverified. Collision boxes are computed from each mesh's own bounding box (binary STL parsed directly in `generate_hand.py`, no extra Python deps); masses are hand-estimated by structural role (proximal/mid/distal phalanx, hand, forearm — same ~5-90g/link range the 1st-generation model used), same "box-formula inertia from an assumed mass, not measured" approach as before.
  - **Driver-joint topology had to be redesigned, not copied**: the source repo's own joint scheme picks the *middle* joint of each 3-joint finger chain as the tendon-driven "actuated" joint (e.g. `index_joint`, between `index1_link` and `index2_link`), with `index1_joint` — upstream, closer to `hand_link` — mimicking it. That's the "upstream mimic" pattern flagged above as non-functional in bullet-featherstone (verified: commanding `index_joint` directly produced ~0 net motion on any joint in the chain, even at high effort, over many seconds). `generate_hand.py` reassigns the driver to whichever joint in each finger chain sits directly off `hand_link` (e.g. `index1_joint`), with every other joint in that chain mimicking it 1:1. This also means the source repo's non-1:1 coupling ratios (e.g. `thumb1 = 0.75 * thumb`, `ring1 = -0.1 * ring`, tuned for the *other* joint being the driver) were dropped in favor of flat 1:1 mimics — still gives a coordinated curl, just not a literal reproduction of the source robot's exact coupling.
  - **Wrist rotation** (`wrist_joint`, `forearm_link` → `hand_link`, axis `(0,0,1)`) is the real InMoov `{l,r}_wrist_roll_joint` from that repo's full-body assembly (`inmoov.urdf.xacro`) — not invented for this project. It's wired to its own `JointPositionController` topic per side (`/inmoov_{left,right}_hand/wrist_joint/cmd_pos`) so it's testable via `gz topic pub`, but nothing in `vision/hand_tracker.py` or `sim/bridge/gz_hand_bridge.py` drives it yet — 2D MediaPipe hand landmarks can't reliably estimate forearm roll without the forearm in view. Left/right have mirrored joint ranges (right: `-π..0`, left: `0..π`) — command within the correct side's range or the position controller silently can't reach the target.
  - **Fixed bug: right hand's ring/pinky curled partway backward.** `generate_hand.py`'s per-side mirror flips joint position (`y`) and `rpy` (`x`-rotation) by `flip`, but originally left every driver joint's rotation `axis` hardcoded to `(0,0,1)` regardless of side. Under a `y`-mirror, rotation *sense* about a `z`-axis reverses (`R_z(θ) → R_z(-θ)`) while rotation about a `y`-axis does not — so `thumb1_joint`/`ring1_joint`/`pinky1_joint` (axis `z`) picked up a handedness error on the right hand that `index1_joint`/`middle1_joint` (axis `y`) never had. The error was invisible on `thumb1_joint` (its `rpy` tilt is only `0.1` rad, so the mis-handled component is tiny) but visible on `ring1_joint`/`pinky1_joint` (`0.7` rad tilt mixes in much more of it), which is why only ring/pinky visibly curled backward, not the whole hand. Fixed by making those three driver joints' axis `(0.0, 0.0, -flip)` instead of a hardcoded `(0.0, 0.0, 1.0)` — left hand (`flip=-1`) keeps the original, already-correct axis; right hand (`flip=1`) gets it flipped. Any new z-axis driver joint added to a finger chain needs the same `-flip` treatment, not a hardcoded axis.
  - `sim/worlds/hand_world.sdf`'s per-model `<pose>` carries the same 180° roll + 90° yaw the 1st-generation model used. **Now visually re-verified in the GUI**: with that roll, the forearm/hand assembly extends *upward* from `base_link`'s origin (fingers up) — `base_link`'s origin is effectively the forearm's cut/elbow end, not the fingertip end. Both hands' mount `z` is set to `0.45` (the workbench top surface added for the environment overhaul, see below) so each hand visually stands up from the table on that elbow end, rather than the earlier `z=1` which floated both hands well above any surface.

### `sim/bridge/gz_hand_bridge.py` — OpenCV vision → Gazebo hand bridge

Lets `vision/hand_tracker.py` (in the `robohand` conda env, host side) drive the simulated hand in real time, in parallel with (or instead of) the real Arduino over serial (`--gazebo` flag, `--no-serial` to skip the real hardware).

- **Why it's a separate process inside the container, not a library call**: `gz.transport13`/`gz.msgs10` Python bindings only exist inside the `robotics-gazebo` image (confirmed via `apt list --installed`); the host's `robohand` conda env has no path to them. `hand_tracker.py` launches it via `docker exec -i robotics_gazebo_sim python3 /sim/bridge/gz_hand_bridge.py` and streams one CSV line per currently-tracked hand per frame — `L,thumb,index,middle,ring,pinky` or `R,...` (curl fractions 0.0=straight to 1.0=curled, same convention as `hand_tracker.py`'s own `curls` dict) — over that pipe. One persistent process/pipe, not a subprocess call per frame. `hand_tracker.py` holds a hand's last-known curls in `smoothed_angles` even after it leaves the webcam frame, rather than snapping it to a default pose on loss — a hand disappearing shouldn't visibly jolt the sim hand.
- `sim/docker/run.sh` sets `--name robotics_gazebo_sim` specifically so this bridge (and any other tooling) has a stable container name to target with `docker exec`.
- **Gotcha #1 — topic name must match the driver joint name exactly.** `hand_world.sdf`'s `JointPositionController` plugins subscribe to e.g. `/inmoov_left_hand/index1_joint/cmd_pos` — the bridge's `JOINT_NAMES` dict must stay in sync with whichever joint `generate_hand.py` picked as each finger's driver (see the hand-model provenance note above), or publishes silently go to a topic nobody's listening on.
- **Gotcha #2 — a single one-shot publish right after `node.advertise()` can be dropped.** Gazebo Transport discovery (multicast, finds existing subscribers) takes on the order of ~1s; publishing once immediately after advertising, then tearing the process down, can race past that window with nothing delivered. Not an issue for the real use case (continuous per-frame streaming for the whole session — discovery settles well within the first second and everything after that lands normally), but worth remembering if writing another one-shot test script against this bridge.
- **Gotcha #3 — the bridge deadbands per-finger before publishing.** `DEADBAND = 0.01`: a curl value within that tolerance of the last one actually sent for that side+finger is dropped rather than republished. This exists because MediaPipe landmark noise passes through `hand_tracker.py`'s EMA largely intact away from the fully-open/closed clipped extremes (see `vision/analysis/signal_chain_walkthrough.ipynb`'s "bonus experiment" cell), so a hand held still but not at a curl extreme was resending near-identical targets every frame. This cuts needless command traffic but was **not** the fix for the rubber-band overshoot issue below — that was a joint-controller torque problem, not a signal-noise problem.

### Known issue (fixed): "rubber band" jitter during and after real motion

Distinct from the rendering-artifact jitter below — this one visibly overshot and bounced back around the target, during vision-driven motion and persisting afterward even with no hand in the webcam frame (ruling out landmark noise, since a static held target shouldn't need continuous correction).

**Root cause: torque saturation, not classic PID underdamping.** Every finger driver joint's `JointPositionController` in `hand_world.sdf` used the same untuned defaults: `p_gain=5`, `d_gain=0.1`, `cmd_max`/`cmd_min=±5` (N·m) — never sized to the model. Computed from the real per-link mass/inertia values in the generated `hand.urdf` (own inertia + parallel-axis contribution from every downstream 1:1-mimicked segment, since a finger's links move together), a 3-segment finger's effective inertia at the driver joint is `I_eff ≈ 5e-5 kg·m²`. Against that, `cmd_max=5 N·m` saturates on any nonzero error and produces angular acceleration around `5 / 5e-5 ≈ 96,700 rad/s²` — a relay/bang-bang controller in disguise, independent of the nominal P/D ratio and independent of whether MediaPipe is currently tracking anything (fires on any target the controller hasn't yet converged to). It also exceeded the URDF's own `effort=2.0` joint limit, so it was never a meaningfully chosen value.

**Fix:** retuned all 10 finger driver joints (5 fingers × 2 hands) in `hand_world.sdf` from the actual link inertia — `p_gain`/`d_gain` picked for critical damping (`d_gain = 2*sqrt(p_gain * I_eff)`) at a settle time of roughly one to two camera frames, `cmd_max`/`cmd_min` capped to the peak torque a critically-damped response actually needs plus margin, not an arbitrary round number:

```xml
<p_gain>0.45</p_gain>
<i_gain>0</i_gain>      <!-- was 0.05: integral windup at this torque scale was another
                              oscillation source, with no steady-state droop to justify it -->
<d_gain>0.0135</d_gain>
<i_max>0.1</i_max>
<i_min>-0.1</i_min>
<cmd_max>1.0</cmd_max>  <!-- was 5: now under the URDF's own 2.0 N*m joint effort limit -->
<cmd_min>-1.0</cmd_min>
```

`wrist_joint` deliberately kept the old defaults — much larger mass (forearm + hand, not a few-gram phalanx) and not vision-driven yet, so it wasn't part of this diagnosis. If wrist control is added later, it needs its own inertia-derived gains, not these finger values.

### Known issue: hand appeared to "jitter" — was rendering, not physics, now worked around

`hand_world.sdf`'s `sun` light has `<cast_shadows>false</cast_shadows>` — deliberately disabled, not an oversight. Symptom: the hand model visibly jittered/shimmered even completely at rest (no commands being sent at all). Diagnosed by subscribing directly to every joint's `axis1.position` at the sim's own ~1kHz update rate for 3s with zero commands published: every joint sat flat to within ~1e-8 rad — i.e. physics/joint state was provably static, so the jitter had to be a rendering artifact, not a control or physics instability.

Best-fit explanation (not filed upstream — a real Gazebo/gz-sim limitation, but this project just works around it locally): the default directional-light shadow-map resolution/depth-bias is tuned for room/building-scale scenes (meters). This hand is ~10cm with many small phalanx meshes packed close together, and at that scale the default shadow map produces shadow acne (flickering self-shadow noise) that reads visually as jitter. If shadows are ever turned back on for this world (e.g. for a nicer screenshot/demo), expect the jitter to return, and either re-disable them or hand-tune shadow map resolution/near-far clip/bias for cm-scale geometry.

### Robotic hand — environment facts to preserve

- Runs in a dedicated conda env, **`robohand`** (Python 3.11) — `mediapipe` has no build for Python 3.13, which is the system-level interpreter here. Always `conda activate robohand` before running anything in `vision/`.
- `mediapipe` 0.10.35 (the version conda installs) **removed the legacy `mp.solutions.hands` API entirely** — only `mediapipe.tasks.python.vision` (`HandLandmarker`) remains. `vision/hand_tracker.py` is written against that Tasks API, not the old one; don't "fix" it back to `mp.solutions`.
- The Tasks API requires an explicit model file, not bundled in the pip package: `vision/models/hand_landmarker.task`, downloaded from `storage.googleapis.com/mediapipe-models/hand_landmarker/...`. If it's missing, re-download rather than assuming the API can run without it (see README.md for the curl command).
- `HandLandmarksConnections.HAND_CONNECTIONS` yields `Connection(start, end)` namedtuples (single int indices), not pairs of connections — a plain list of landmarks, not the old `.landmark` sub-attribute.

## Environment facts to preserve

These constraints came from real troubleshooting and should not be re-derived or second-guessed without new evidence:

- **Working NVIDIA driver range is R570–R580** (specifically `nvidia-open-dkms` 580.119.02 is confirmed working). Driver 610+ segfaults inside Isaac Sim's bundled RTX libraries (`librtx.scenedb.plugin.so`, `carbOnPluginStartup`) because its ABI is incompatible. Driver 565.x fails to build against kernel ≥6.12 (missing `phys_to_dma`, `dma_is_direct`, `ioremap_driver_hardened_wc`).
- **Isaac Sim 4.5.0 does not work** on this setup (requires driver ≤565, which conflicts with the kernel constraint above). **5.1.0-rc.19 segfaults** (unstable RC). Only **5.0.0** is confirmed stable.
- The **LTS kernel and the NVIDIA driver packages are both pinned** via `IgnorePkg` in `/etc/pacman.conf` to prevent pacman from silently upgrading past the working versions.
- Docker's default runtime must be set to `nvidia` in `/etc/docker/daemon.json` for `--runtime=nvidia` container GPU access to work.
- `--network=host` is required on the `docker run` for the WebRTC streaming client to reach port 49100; the media stream itself uses UDP port 47998.
- Only one WebRTC streaming client can connect at a time; NVENC (present on RTX, absent on A100) is required for streaming.
- ROS2 Humble is bundled inside the `nvcr.io/nvidia/isaac-sim:5.0.0` image — no host ROS2 install is needed.
- If the pinned R580 driver ever breaks, the documented fallback is R570 (`570.153.02-1`), from the same Arch Linux archive.

## Shell conventions

All example commands in this repo's docs are written for **fish shell** (not bash) — e.g. `set VAR value` instead of `export VAR=value`, `set -a pkgs ...` for array append. Keep this convention when adding or editing commands in `isaac-sim-setup.md` or elsewhere in this repo.

## Common commands (from isaac-sim-setup.md)

Pull and run Isaac Sim headless with WebRTC streaming:
```fish
docker run --rm --runtime=nvidia --network=host -e ACCEPT_EULA=Y -e PRIVACY_CONSENT=Y nvcr.io/nvidia/isaac-sim:5.0.0 ./runheadless.native.sh
```

Run a standalone Python script without a streaming viewer:
```fish
docker run --rm --runtime=nvidia -e ACCEPT_EULA=Y nvcr.io/nvidia/isaac-sim:5.0.0 ./python.sh /isaac-sim/standalone_examples/api/omni.isaac.core/hello_world.py
```

Verify the active driver version:
```fish
nvidia-smi
```
